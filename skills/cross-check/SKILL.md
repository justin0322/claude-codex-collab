# cross-check：Claude Code × Codex 交叉審查

## 分工
- **Claude**：主要開發者。負責寫審查說明（brief）、執行、逐條驗證 Codex 的意見、寫紀錄。
- **Codex**：唯讀的獨立審查者，不能修改 repo。Codex 會讀 repo 的 `AGENTS.md`，專案規則寫在那裡。
- **使用者**：最後裁決。有沒有效、要不要改、要不要 merge，都由使用者決定。

## 怎麼呼叫
codex-collab 在每次使用者發訊息時附給你的 `[codex-collab]` 提醒裡，有這個 session 完整的呼叫指令：
`COLLAB_SID=<sid> bash <plugin>/backend/run_codex.sh new <G1|G2|G3|G4|CONSULT> <slug> <brief 檔> [base_ref]`
- 提醒說「Claude 單獨模式」或「這個對話已關閉 Codex 協作」時，不要呼叫 Codex。
- G1–G4 通常要跑 5～30 分鐘，用 Bash 的背景執行，等完成通知，不要輪詢。CONSULT 用同步等待（`CODEX_TIMEOUT=360`）。
- **失敗就停**：exit 不是 0 時，照實告訴使用者錯誤訊息，不重試、不自己補一份審查結果。exit 7 代表額度不足。
- 結果在 `<review_dir>/raw/<run_id>/result.json`。

## 四個關卡
使用者通常用白話說（「審設計」「審程式」「驗數字」「審結論」），對應到下面的代號；參數寫「審設計」和寫「G1」意思相同。
跟使用者說話時用白話名稱，代號只在指令、檔名裡用。

| 白話名稱 | 代號 | 時機 | 審查對象 | brief 要寫什麼 |
|---|---|---|---|---|
| 審設計 | G1 | 設計和判定規則寫好、**還沒看結果** | 設計文件＋腳本 | 設計文件路徑、腳本路徑、要回答的問題 |
| 審程式 | G2 | 程式已 commit、**還沒執行** | `base...HEAD` 的 diff＋相關程式 | 要跑的指令、預期輸出、基準 branch |
| 驗數字 | G3 | 執行完、整理出表格之後 | 原始輸出 vs 結果表 | 原始檔路徑、指標定義、結果表位置（Codex 會在重算完才看） |
| 審結論 | G4 | 寫進論文、報告、文件或簡報前 | 結論文字 | 文字所在檔案與段落、對應的實驗紀錄 |

## 寫 brief（盲審，最重要的一步）
把 brief 寫到暫存目錄。
- **要寫**：要回答的問題、審查範圍（檔案路徑）、背景事實、Codex 在 repo 外找不到的資訊（會議決定、限制、時程）。
- **不能寫**：自己的判斷、預期結果、懷疑的問題、「我覺得沒問題」這類話。G3 不能寫自己算出來的數字。
- 不要把程式碼貼進 brief，給路徑讓 Codex 自己讀。寫完自己檢查一遍：這份 brief 有沒有暗示答案？

## 逐條驗證
Codex 每次都會找到東西，它是懷疑者，不是裁判。對每一條 finding：
- 回到 code 或資料親自確認，判定為：
  - **確認**：附上自己查證的 檔案:行號 或指令輸出。
  - **駁回**：附上理由和證據。
  - **爭議**：雙方各有道理，或需要使用者才知道的資訊。
- 不要因為 Codex 語氣肯定就接受，也不要因為和自己的想法不同就駁回。
- G3：把 Codex 的 `numbers` 和結果表逐格對照，有差異就自己再算一次，找出哪一邊錯了。
- `not_checked` 列出的部分，在紀錄裡標明「本次未審」。

## 追問（最多一輪）
只有影響結論的「爭議」才追問，這時可以附上 Claude 的反證：
`COLLAB_SID=<sid> bash <plugin>/backend/run_codex.sh followup <run_id> <question 檔>`
腳本會擋第二輪。追問後仍有爭議，就交給使用者裁決。

## 寫審查紀錄
寫到 `<review_dir>/<run_id>.md`：日期／branch／HEAD／run_id、審查對象、Codex 總評、逐條判定表（# ／嚴重度／問題／位置／Claude 判定／依據）、G3 數字對照、本次未審、待使用者裁決。
回報使用者時一次只講最重要的兩三項，其他的指向紀錄檔。**不要自己動手修**，修不修由使用者決定（自動審查訊息另有規定的除外）。

## 自動模式（codex-collab mod）
- **改檔後的審查（AUTO）**：回合結束時，若程式或文件有變更，就在背景送審。審完後，mod 會送出 `[codex-collab] Codex 自動審查完成…` 訊息，照訊息裡的步驟處理即可。
- **輪次**：使用者的新要求是第 1 輪；Claude 依審查結果修改後，下一次審查是下一輪；到 `max_rounds` 就停止送審，還沒解決的做成爭議卡交給使用者。
- **額度**：Codex 週額度達到 `auto_limit`%，或 Codex 回報額度用完時，切換為 Claude 單獨模式；這段期間的變更會記下來，恢復後自動補審。
- **使用者指令**：`/collab`（狀態）、`/collab off`／`on`（只影響這個對話）、`/collab pause`／`resume`（全部對話）、`/collab skip-g2`。G2 守門擋下時，由使用者決定是否略過，Claude 不要自己繞過。

## 討論模式（CONSULT）
遇到研究或設計討論（下一步、取捨、結果解讀），或使用者說「問 Codex」時：
1. **先把自己的看法寫在暫存檔**（不給 Codex），避免之後被 Codex 的答案牽著走。
2. 寫 brief：問題本身、相關事實與檔案路徑、目前狀態與限制。Codex 讀不到 Claude 的記憶，需要的背景要寫進去。**不寫 Claude 的看法**。
3. 用 `CONSULT` 執行，同步等待。
4. 用這個格式回覆：
   - ✅ 共識：兩邊都認為…
   - ⚖️ 分歧：Claude 主張…／Codex 主張…／怎麼做能判斷誰對
   - 💡 Codex 想到、Claude 沒想到的：…
   - → 綜合建議（最後由使用者決定）
5. 分歧如果是查得到的事實，先查清楚再回覆，不把它當成爭議。討論不追問、不來回辯論。
6. 失敗或額度不足時，照實說「這次沒有 Codex 的意見」，由 Claude 單獨回答。

## 注意
- Codex 讀到的內容會送到 OpenAI，Claude 讀到的則送到 Anthropic；有授權或隱私限制的資料，請在 `AGENTS.md` 寫明。
- 兩邊都說沒問題，不代表正確：如果輸入檔本身就錯，兩個模型會一起錯。G3 一定要從原始輸出重算。
